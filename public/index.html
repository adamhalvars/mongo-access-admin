How access works in MongoDB

In MongoDB a user gets access through roles, and each role is granted on a specific database. The user signs in against their auth database, but that does not decide what they may do. Only the roles do.

Overview

The user signs in against their auth database and gets their access from the roles, each one on a specific database. Without a role on a database, like finance here, the user has no access to it.

The auth database

The auth database is the database where the user was created and where they sign in. It does not decide which databases the user may use. Only the roles do that.

  • Name + auth database identify the user. anna in admin and anna in shop are two different users, each with their own password and roles.
  • When signing in, the auth database is given with authSource, for example mongodb://anna:password@server:27017/?authSource=admin. Without authSource the database in the address path is used, and if there is none, admin is used.
  • All users are stored in the same place, in admin.system.users, whatever their auth database.
  • Access can be granted to any database, independent of the auth database. A user in admin may well only have access to shop.

Recommendation: create all users in admin. Then everyone signs in the same way, and nobody has to remember where they were created. In Access Admin the auth database is shown under the user's name, as "auth: admin".

Access to different databases

Access is always granted as a pair: a role and the database the role applies to. The same role on two databases is two separate grants.

User Role Database Result
anna read shop Can read everything in shop
anna readWrite hr Can read and change everything in hr
anna (none) finance No access to finance
  • One grant per database. If someone needs access to three databases they get three grants, or one custom role that covers all three (see Custom roles).
  • Roles ending in AnyDatabase apply to every database except local and config, including databases created later. They are always granted on admin.
  • Roles on admin are special. A role there can affect the whole server, so only grant roles on admin when it is really needed.
  • Access can be granted in advance. You can grant access to a database that does not exist yet. It applies once the database is created.

Custom roles as groups

A custom role bundles privileges under one name, so you can give the same access to many users at once. Change the role and the access changes for everyone who has it.

A custom role has two parts:

  • Privileges: a resource (a database, a collection or the whole server) and the actions allowed on it, for example find and insert on shop.orders.
  • Inherited roles: other roles, built-in or custom, whose privileges the role takes on.

Where the role is created decides what it may contain:

Created in May contain privileges in May inherit roles from
admin Every database and the whole server Every database
Another database, e.g. shop Only shop Only shop

A role is identified, just like a user, by name + database: analyst@admin and analyst@shop are two different roles. Recommendation: create custom roles in admin, so they can span several databases.

Example: the role analyst@admin has find on shop.orders and inherits read on hr. Anyone with the role can read everything in hr but only the orders collection in shop. In the matrix this shows as Read in hr and a striped cell, Read (partial), in shop.

How access adds up

A user's access is the sum of all their roles. One role can never take away access that another role gives, because MongoDB has no rule for denying.

  • More access always wins. If anna has both readWrite and read on shop she can write. Adding read restricts nothing.
  • To reduce access, remove the role that gives it. Click the cell in the matrix to see which roles those are.
  • Inherited roles count at every level. If a role inherits another that in turn inherits a third, the user gets the privileges of all three.
  • Privileges can apply to a whole database or to individual collections. If they only apply to some collections, the cell in the matrix is striped and marked "partial".
  • Changes take effect immediately. MongoDB checks privileges on every operation, so a removed role stops working even for someone who is already signed in.

Pitfalls and good habits

Several roles give full power in practice, because whoever has them can grant more access to themselves.

Role Why it is dangerous
userAdmin or dbOwner on a database Can grant itself any privilege in that database
userAdmin or dbOwner on admin Can grant itself everything on the whole server
userAdminAnyDatabase Can grant itself everything. MongoDB calls it effectively a superuser
root Has everything from the start

Treat these roles like root and give them to as few people as possible. In the matrix and the report they show as Owner or with the +access marker. The account Access Admin itself uses needs userAdminAnyDatabase, so protect connections.json accordingly.

Good habits:

  1. Grant the least access possible. Read access is enough more often than you might think.
  2. One account per application and environment, with only the role the app needs, usually readWrite on its own database. Never give root to an application.
  3. Personal accounts for people, no shared accounts. Then the audit log shows who did what.
  4. Use custom roles as groups, for example developer and analyst, instead of granting many roles one by one.
  5. Remember that readWrite can also drop collections. If someone should only add data, a custom role with find and insert is safer.
  6. Do an access review regularly. Export the Excel report and have the owners confirm that the access is right.
  7. Check that authentication is enabled on the server (security.authorization: enabled). Otherwise anyone can do anything, and Access Admin shows a warning in the header.
  8. MongoDB Atlas is not managed here. Atlas does not allow user and role commands over the database connection. There, users are managed in the Atlas web UI, API or CLI.

How to do it in Access Admin

Choose the right connection in the menu at the top before you start. Prod is marked in red.

A new colleague who needs to read a database

  1. Users → New user. Enter the name, leave the auth database as admin, click Generate and then Copy for the password.
  2. Under Access choose read and the database. Click Create user.
  3. Send the password securely and ask the person to change it.

A new account for an application

  1. New user with a name that shows app and environment, for example orderapp-prod.
  2. Access: readWrite on the app's database, nothing else.
  3. Give the connection string with authSource=admin to the people who run the app.

The same access for several people

  1. Roles → New role. Create it in admin and give it privileges (the Read only and Read + write buttons help) or let it inherit built-in roles.
  2. Add the people under Members on the role.

Remove access

  • A role from one person: click × on the role in the Users tab, or click the cell in the Matrix and choose Remove the role. You are asked whether you are sure.
  • Someone who leaves: Users → Delete and type the name to confirm. All access disappears immediately.

Find out who has access to something

  1. Open Matrix and choose the database in the filter, or choose Write access or more.
  2. Click a cell to see exactly which role gives the access.

Access review

  1. Matrix → Export to Excel → All connections.
  2. The Overview sheet gives the key figures per connection. The Details sheet can be filtered by user or database.

Troubleshooting

Message or problem Common cause What to do
Authentication failed Wrong password, or wrong auth database in authSource Check that authSource is the database where the user was created. In the app it is shown as "auth:" under the name
not authorized on shop to execute command The user lacks a role that allows that action in shop Click the cell for shop in the Matrix to see what is missing. Grant e.g. read or readWrite
The user cannot see the database in their tool They have no role in that database Grant a role on the database. Tools like Compass only show databases the user has access to
User "x@admin" already exists The user already exists in that auth database Grant the existing user more access instead of creating a new one
Could not find user Wrong auth database given Check the auth database under the name in the Users tab
Could not connect (in Access Admin) The server cannot be reached, or the password in the connection is wrong Connections → Edit → Test connection
